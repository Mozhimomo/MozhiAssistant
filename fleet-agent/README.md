# 舰队智能体

目前已实现模型层、异步 Planner、Executor、结果检查器 Monitor、Agent 循环，以及购买、出售、移动、跟随、回归、跑商计算、到站采购规划和向玩家转账八个工具，包括最近 20 步执行结果的滑动窗口。`game.FleetRuntime` 已接入游戏主循环、聊天命令、状态面板和 JSON 存档。实际航行和模型响应仍需游戏内验证。

## 模型层

两个模型都是 Java 17 record，只描述计划内容，不保存执行状态，也不依赖游戏 API 或 LLM。

| 模型 | 字段 | 含义 |
| --- | --- | --- |
| `Plan` | `id` | 计划 ID；创建新计划时分配新 ID |
| `Plan` | `goal` | 这份计划要达成的目标 |
| `Plan` | `steps` | 按执行顺序排列的非空步骤列表，步骤 ID 不可重复 |
| `Step` | `id` | 步骤 ID；同一动作跨计划继续执行时保留 |
| `Step` | `tool` | 工具名称，由 Executor 匹配已注册的注解方法 |
| `Step` | `arguments` | 工具参数，只允许 JSON 值；无参数时传空 Map |
| `Step` | `description` | 用于界面展示的步骤说明 |
| `Step` | `expectedOutcome` | 给监控器参考的预期效果描述，不是实际执行结果 |

`Plan.create(...)`、`Step.create(...)` 为新对象生成 UUID；构造器可使用已有 ID 恢复数据。改变动作或参数时应创建新步骤。步骤 ID 仅提供身份，后续协调器仍需核对实际执行记录和动作内容，不能仅凭 ID 决定是否跳过或续接。

列表和嵌套参数在创建时拷贝并设为只读，避免规划线程与游戏主线程共享可变数据。构造器拒绝空白必填字段、重复步骤 ID、非有限数值，以及游戏对象等非 JSON 参数。

```java
Step move = Step.create("MOVE_TO", Map.of("destinationId", "jangala"),
        "前往 Jangala", "抵达目标市场");
Step buy = Step.create("BUY", Map.of("item", "supplies", "quantity", 100),
        "购买补给", "补给增加 100");
Plan plan = Plan.create("采购补给", List.of(move, buy));
```

这里展示模型的构造方式，实际动作需要提供下文动作表中的完整参数。模型只校验通用结构，具体动作的参数、前置条件和完成判定由动作实现校验。当前步骤下标和进度版本由 Agent 保存；全部步骤成功后由 LLM 额外验收原始目标，确认达成才结束任务。

## 规划器（Planner）

`planning.Planner` 接收 `PlanningRequest`，通过 `plan(request)` 立即返回 `Future<PlanningResult>`。配置读取、LLM 客户端初始化及规划请求在专用后台线程执行，不访问游戏对象。可以传配置 URL，也可以注入已有的 `LlmClient`。

配置 URL 入口支持 `fleetPlannerMaxOutputTokens`、`fleetPlannerThinkingMode` 和 `fleetPlannerReasoningEffort`，分别覆盖舰队规划的输出预算与思考参数，省略时继承聊天配置。模板将规划输出预算设为 32768，包含思考和计划正文；思考参数默认继承聊天配置。

主规划或目标验收遇到 `LENGTH` 截断时，使用同一快照独立恢复一次，不续写截断内容、不执行或重放游戏动作。恢复请求沿用原模型与输出上限；原请求明确开启思考时，仅本次恢复关闭思考，其他已配置的推理强度降为 low。要求重新生成简短完整的决策，结果仍经过正常校验。恢复失败后沿用既有失败处理，不无限重试；正常请求和本地配置不变。恢复用量单列为 `planning_recovery`。

请求包含任务 ID、快照版本、原始目标、世界状态文本、执行历史快照、触发原因、当前计划和 `ActionSpec` 动作列表。动作契约说明前提与效果，并列出允许的参数、JSON 类型及必填项。规划器校验动作名、参数名和类型；具体数值范围及游戏前提由后续执行器校验。

| 结果 | 含义 |
| --- | --- |
| `REPLACE` | 返回新计划，计划目标沿用原始目标，计划 ID 由应用分配 |
| `KEEP` | 返回原计划对象，保留步骤身份，不重置执行进度 |
| `GOAL_REACHED` | 模型认为目标已达成，Agent 核对任务和进度版本后结束任务 |
| `BLOCKED` | 当前无法制定可执行计划，提供阻碍原因 |

模型只能指定 `reuseStepId` 来建议续接当前计划中未完成的步骤。代码会核对动作和参数一致，并复用原步骤对象；新步骤由代码生成 ID。不存在、已完成、重复复用或修改参数的复用请求会被拒绝。Agent 丢弃执行进度变化前生成的计划，并阻止续接刚失败的步骤。相同语义但不同 ID 的动作仍依赖 Planner 结合历史判断，Agent 不额外做语义审核。

响应通过 `LlmClient.aiService(...)` 转成草案，沿用现有连接、输出预算、思考和结构化输出配置。每步草案使用 `tool` 指定工具；为兼容严格 JSON Schema，动态参数使用 `argumentsJson` 文本传输，解析及校验后进入 `Step.arguments`。重复 JSON 键、非对象参数、尾随内容和无效计划都会使 Future 异常完成，不回退为成功或保留计划。

### 注解工具注册与执行

八个内置工具都使用 LangChain4j 的 `@Tool` 和 `@P(name=..., value=..., required=...)` 声明。`FleetToolRegistry` 在注册时扫描公共方法、缓存反射入口，并从同一份注解生成 `ActionSpec` 参数契约。Planner 接收 `tools` 清单，只生成有序调用请求；Executor 查表绑定参数并反射调用，无 LLM。工具名为 BUY、SELL、MOVE_TO、FOLLOW_FLEET、RETURN、CALCULATE_TRADE_ROUTE、PREPARE_TRADE_HOP、TRANSFER_TO_PLAYER；RETURN 仍由 Agent 的返航授权控制。子智能体只能将自身星币转给玩家，不能从玩家账户取款；主对话仍保留双向转账。

工具方法返回 `ExecutionResult`；`Step` 和 `ActionContext` 由主线程本地注入，不属于模型参数。可选参数使用包装类型，省略时为 null，由工具实现应用业务默认值。跨帧重复调用复用同一工具实例和步骤 ID；pause、stop、cancelBackground 沿用现有生命周期。Executor 缓存成功和失败终态，避免重复成交，Monitor 和 Agent 继续负责结果检查及推进。

新存档的步骤使用 `tool/arguments`，读取时接受原有 `action/parameters`；既有 Java 访问入口仍保留。已有自定义 Action 扩展可继续注册，但内置工具不再手写独立契约，也不通过类名或模型提供的方法名任意反射。异常解包后保留原始类型，资产不确定等错误仍按原流程处理。

同一快照的重复请求共用进行中的 Future。忙碌时提交不同快照会立即报错，调用方应合并周期触发，等待当前结果后使用新快照再次规划，避免请求堆积或每 15 秒取消尚未完成的请求。新用户任务可以显式 `cancel()` 后提交；`close()` 取消请求并关闭后台线程。底层请求如果忽略中断，后续请求仍需等待它完成或超时，但取消的 Future 不会返回迟到结果。`isStopped()` 可供后续类加载器清理逻辑使用。

结果带回原任务 ID 和快照版本。调用方应在游戏主线程轮询 `isDone()`，完成后再读取结果、核对任务与实际进度并决定是否接纳。Planner 不自动替换执行中的计划，也不启动周期计时器。

## 最近 20 步执行历史

### 模型上下文与用量

`PlanningPrompt` 单独生成模型请求，原始 `PlanningRequest` 和存档仍保留完整数据供校验。请求按固定动作契约、目标、剩余计划、最近历史、世界状态、触发原因与版本排列；嵌套对象键稳定排序，市场/商品列表按身份排序，世界状态以 JSON 对象嵌入，不做二次字符串转义。缓存仍由服务商决定，不保证命中。

模型只收到未完成步骤；最近 20 步保留动作参数、状态、实际结果及金额，不重复 description/expectedOutcome，计算返回的完整 Plan 改为生成步骤数，具体剩余步骤在 currentPlan 中。已完成 ID 集合留在本地，发给模型的是累计完成数。

世界快照只列目标、剩余计划及已环绕市场，库存只列提及的商品或舰船；目标相关星系按需提供，不发送全星区目录。玩家舰队只提供位置，分舰队保留资源、舰船和经济商品/目标相关货物。省略的库存和装备不代表不存在。自主跑商计算器仍搜索全市场，资源采购仍提供可达候选渠道。

完整交易收据本地保留；模型使用 `worldState.tradeSummary` 的总支出、总收入、现金净流入及按商品汇总，加上最近执行结果中的收据。现金净流入不是净利润，当前余额仍是“拥有多少星币”的验收依据。`unknownAmountTrades` 标记无法计价的历史交易，近期收据已计入汇总，不能重复累加。

每 15 秒周期先由独立轻量模型 `ReplanCheckService` 判断 KEEP/REPLAN；KEEP 不调用主模型，REPLAN 再由主模型生成完整决策。检查快照不带动作契约和市场目录，包含目标、剩余步骤、资源、最新结果与受控舰队状态。后勤建议同样先交轻量模型判断；新任务存在建议时先判断建议，再由主模型生成初始计划。执行失败及最终目标验收直接用主模型。两路默认同用 deepseek-flash，可用 `cheapModelName/cheapBaseUrl/cheapApiKey` 独立设置轻量路由，空项继承主模型；周期检查不生成计划或结束任务。

内部 UI 快照的 `state.usageStatistics` 提供当前生命周期的用量汇总；对话状态摘要省略技术诊断。`data/diagnostics/usage-fleet.jsonl`、`usage-chat.jsonl` 记录分类、字符数、耗时、输入/输出 token、缓存命中/未命中；类别包括 initial、periodic_check（周期轻量判断）、resource_check（后勤建议轻量判断）、periodic（升级后的主模型规划）、replan、review、chat、notification、summary。取消和过期结果另记事件。模型相同时不会产生单价差异，节省来自输入精简及 KEEP 时跳过完整规划。

用量取服务商响应，缺失值写 null；失败/取消可能已计费，SDK 内部重试可能不可见。统计中的 known* 仅为已报告数值，结合 usageReportedCalls/cacheReportedCalls 判断覆盖率。日志不写提示词、回复、思考、密钥或异常正文；单文件 5 MiB 轮转，保留一份旧文件，日志目录不上传 GitHub 或进入发行包。

`model.ExecutionResult` 包含步骤定义、`RUNNING / WAITING / SUCCEEDED / FAILED` 状态、实际结果说明及可选的 `generatedPlan`、`tradeReceipt`。Executor 每轮反馈自动写入共享的 `ExecutionHistory`；外部接入时不要重复记录。

- 窗口从旧到新保留最近 20 个步骤的最新结果，包含成功、失败及仍在执行的步骤。
- 同一步骤的多轮反馈更新原记录，不会让航行等长动作挤满窗口。
- 超出窗口时移除最旧的详细结果；已成功步骤的 ID 单独保留，直到该任务结束。
- 每次规划使用不可变的 `snapshot()`，包含动作、参数、状态及实际效果或失败原因；提交后的执行更新不改变已有请求。
- Agent 启动新任务时清空共享历史和终态缓存。存档通过 `Agent.State` 和 `Executor.State` 保存历史窗口、完成身份、终态缓存和当前步骤。

历史记录与规划请求示例（使用 Executor 时，它会代为调用 `history.record`）：

```java
ExecutionHistory history = new ExecutionHistory(); // 一个任务持有一份
history.record(new ExecutionResult(step, ExecutionResult.Status.SUCCEEDED, "已实际买入 100 个补给"));
PlanningRequest request = new PlanningRequest(taskId, revision, goal, worldState,
        history.snapshot(), "步骤完成后重新规划", actions, currentPlan);
Future<PlanningResult> pending = planner.plan(request);
// 后续游戏更新中判断 pending.isDone()，再读取和核对结果。
```

## 执行器（Executor）与动作

`execution.Executor` 在创建它的游戏主线程运行，不调用 LLM。`execute(plan, stepIndex)` 只推进 Agent 指定的一步，返回 `ExecutionResult`；成功后不会自动进入下一步。`execute(step)` 也可用于执行单个步骤。

所有动作放在 `actions/`：

| 动作 | 实现 | 参数和完成条件 |
| --- | --- | --- |
| `BUY` | `BuyAction` | `marketId`、`submarketId`、`itemType`、`itemId`、`quantity`；先实际入轨，再转移库存和扣款 |
| `SELL` | `SellAction` | 参数同 BUY；实际移出自有库存，转入交易区并收款 |
| `MOVE_TO` | `MoveToAction` | `destinationId` 为实体、市场或星系 ID；航行并确认实际环绕目标后成功 |
| `RETURN` | `ReturnToPlayerAction` | 无参数；驶向玩家，靠近后合并全部舰船、军官、货物和星币，最后移除分舰队；必须位于计划末尾 |
| `FOLLOW_FLEET` | `FollowFleetAction` | `targetFleetId`，或用 `player` 跟随玩家；按 RETURN 同样的 GO_TO_LOCATION 方式追赶，靠近后 HOLD，目标远离后继续追赶，不合并资产，持续 RUNNING，必须位于计划末尾 |
| `TRANSFER_TO_PLAYER` | `TransferToPlayerAction` | `amount` 为本次转账金额；仅做前向校验，余额充足即转账，允许转出全部余额；相同步骤不会重复扣款 |
| `CALCULATE_TRADE_ROUTE` | `CalculateTradeRouteAction` | 可选路线与资源约束；按真实数据生成 `Plan`，通过 `ExecutionResult.generatedPlan` 返回 |
| `PREPARE_TRADE_HOP` | `PrepareTradeHopAction` | 计算器生成的到站决策；更新本地货架后生成本段后勤采购、买入、移动和出售步骤 |

`itemType` 支持 `COMMODITY`、`WEAPON`、`FIGHTER`、`HULLMOD`、`SPECIAL`、`SHIP`。普通物品使用规格 ID；舰船使用实例 ID，数量必须为 1。特殊物品可通过 `itemData` 指定实例数据，同一物品 ID 对应多种数据时必须明确选择。数量必须为 1 至 1000000 的整数，不能出售分舰队最后一艘舰船。

模型返回 BUY/SELL 小数数量时，Planner 在创建 Plan 前向下取整，并同步修正步骤描述；例如 16.9 变为 16。取整后不足 1 或超出有效范围的计划被拒绝，不自动补成 1。跑商算法本身生成整数数量。执行器继续严格执行 Plan 的整数数量，不在成交时隐式更改数量；金额、航行时间及资源余量仍可保留小数。

库存观察同时提供原始 `quantity` 和取整后的 `wholeQuantity`。库存 0.9 表示没有可购买的整件商品，不是购买指令；到站计算不会为不足一件或缺货商品生成买卖步骤。缺货错误明确报告市场、交易区、请求数量、实际库存和可成交整数数量；首次交易失败的动作参数及错误写入游戏日志，供排查使用。

买卖在执行当次更新并读取指定交易区的实际库存与价格，计入关税；数量或资金不足时整步失败，不部分成交，不代替 MOVE_TO 导航。交易通过 NPC 的资产转移完成，不模拟玩家交易 UI 或模组商店的专用交互脚本。免费仓储与隐藏交易区不可用于买卖。

成功买卖返回 `ExecutionResult.tradeReceipt`：`creditsSpent` 为购买实际支出，`creditsReceived` 为出售实际收入，另一方向为 0；`quotedTotal` 为含税报价。实际收支按游戏星币余额差计算，大额余额的浮点取整可能使它与报价稍有不同。失败或未成交时没有收据。收据随执行历史、终态缓存和存档保存，重复执行同一步返回原收据，不再次扣款或收款。旧存档缺失收据表示金额未知。

内部 UI `view()` 仍保留 `state.tradeReceipts` 及步骤收据。对话 `status` 和命令响应返回摘要：任务、实时后勤、计划总进度、最多三个后续步骤及 tradeSummary。逐笔查询使用 `tradeReceipts` 命令（工具 `getMozhiTradeReceipts`）：传入当前 `taskId`、从 0 开始的 `offset`、1–50 的 `limit`，沿 `nextOffset` 翻页，-1 表示当前已读完；任务变化报错，避免跨任务混账。规划和验收使用汇总及最近收据。以 `stepId` 去重，不把明细与累计汇总重复相加。买卖命令接受不代表成交。

游戏暂停、受控舰队战斗或跃迁期间返回 WAITING。RETURN 也等待玩家结束战斗和跃迁；已有原生航行由游戏继续更新。MOVE_TO 下达环绕任务时仍返回 RUNNING，实际 OrbitAPI 确认入轨才返回 SUCCEEDED。`stop()` 可停止未完成的移动并保留已有轨道；之后可以续接同一步骤。

执行器缓存成功和失败的终态，同一步骤的重复调用返回原结果，防止重复买卖与合并。失败步骤不会因下一轮调用而自动重试；需要 Agent 决定是否创建新步骤。相同 ID 不能改变步骤定义。终态缓存、历史和当前步骤都随游戏保存，恢复时沿用实际进度。

购买和出售在成交前检查真实库存、资金及交易条件，随后按计划数量转移并结算，不再核对成交后的货物数量、余额或舰船转移结果；游戏自动清理不足一件的库存尾数不会导致交易失败。游戏接口实际抛出异常时，买卖及派遣仍按逆序恢复并核对变更。恢复无法确认时，`isBlocked()` 为 true，Agent 停止任务；新任务和读档均不能清除这个阻塞。RETURN 到达后直接合并舰船、军官、货物和星币，移除分舰队即完成，不进行结果数量校验或事务回滚。

原生货舱的商品小数累计量不包含在 `CargoAPI.getQuantity()` 中。资产转移与回滚使用货堆加 `CargoData.getPartial()` 的实际总量；回归也合并只有小数余额而没有可见货堆的商品。该适配针对本项目的 0.98a 游戏库，并有真实 `CargoData` 回归测试。

通过 Executor 调用动作，以确保主线程检查、状态检查、终态缓存和执行历史都生效：

```java
ExecutionHistory history = new ExecutionHistory();
Executor executor = new Executor(ActionContext.forFleet(controlledFleet), history);
// executor.actionSpecs() 提供给 PlanningRequest，确保规划和执行使用同一份动作契约。
ExecutionResult result = executor.execute(plan, currentStepIndex);
// 由 Agent 根据 result 和实际世界状态决定推进、等待、结束或重规划。
```

`ActionContext` 持有实时游戏对象，仅供主线程使用；Planner 仍然只接收不可变的文本及数据快照。

## 跑商决策工具

`trading/` 按 `starsector-trade-route-planner-master` 的计算流程独立实现，不引用其源码、类或 JAR。游戏集成沿用本项目的 Plan、买卖回执与模型调度。

1. **轻量快照**：只读取经济市场的供需、稳定度与货架估算。未访问市场按原生库存上限和稳定度估算；已访问市场只读 `getCargoNullOk`，按补货/回落速度推算，再乘 0.9。不初始化或刷新远方货架，不预采集所有数量报价。交易范围与参考实现一致，为 16 种经济货物，排除人员。
2. **候选粗筛**：先筛首站距离，再用来源过剩、目的地短缺、可买数量、空间和旅时评分。候选图约 200 市场，保留首站池；市场总量不超过上限时省略全图筛选。商品先按市场建索引，每对市场的粗评分只算一次，排序只比较缓存分数。每排好一个来源就立即精算其出边，避免全部来源排序耗尽预算后仍零报价。首轮每个起点最多精算 48 个目的地（总量软预算 960），第二轮每个候选再精算 16 个未计算目的地。
3. **装货计算**：精确价格与买卖执行共用整批含税取整口径；资金上限用二分查找，数量测试最大值、分数档位、经济单位和固定数量。按单位空间利润排序，黑市优先、开放市场补充，最后用剩余资金装燃料。路程、整批报价与可复用货单只在本次计算内缓存。
4. **限时搜索**：默认 2 秒软预算，约 55% 用于建图及精确报价，其余用于双站闭环种子和优先队列分支搜索；队列最多 4000 项。评分为贸易差价 /（贸易航行天数 + 0.5 × 抵达首站天数）。预算覆盖精算和搜索；初始轻量采集另计，游戏暂停不计入预算。全程不调用 LLM，游戏 API 只在主线程读取；采集和搜索按约 4ms 软时间片推进，单次游戏 API 调用不能抢占。
5. **到站重算**：路线 Plan 先移动到首站，随后每段一个 `PREPARE_TRADE_HOP`。该决策只刷新当前市场的开放/黑市货架，按真实资金、容量及下一站最新价格生成 `BUY → MOVE_TO → SELL`；采购不足的燃料/补给也明确写成 BUY，沿用原参数，不强加固定保留量。若失去盈利货物，则清空货单、保留空载行程。实际无法完成本段采购或航行时返回普通动作失败，由 Agent 重规划。
6. **结果与诊断**：返回有界启发式结果，不保证全局最优。日志记录快照耗时、起点数、已排序来源数、粗评分市场对数、盈利候选航段数、精算市场对数、整批报价次数、展开/剪枝次数、建图与搜索耗时。预算耗尽且未得到路线时明确报告搜索未完成，不能据此推断不存在利润或资金、容量不足；零报价会单独提示。进度文字区分快照、精算和搜索，不再把“读取过市场”显示为报价已采集完。

可选参数（均可省略）：

| 参数 | 默认值 | 含义 |
| --- | --- | --- |
| `maxStops` | 4 | 不重复市场数量，2–6；闭环另加返回起点的一段 |
| `maxDays` | 30 | 生成路线的预计天数上限，含抵达首站 |
| `maxStartDistanceLy` | 10 | 首站距离上限，同星系市场不受此限制 |
| `maxSpend` | 1000000000 | 每段采购预算上限，实际还受舰队资金限制 |
| `minProfit` | 1 | 整条路线最低预计贸易利润 |
| `reserveCredits` / `reserveFuel` / `reserveSupplies` | 0 | 保留资金及航程后保留物资 |
| `allowBlackMarket` | true | 是否允许考虑黑市；玩家明确排除时设为 false |
| `closedLoop` | false | 最后返回首个市场；不等于回归玩家 |
| `commodityIds` | 空列表 | 允许交易的经济商品 ID；空表示全部 16 种，不含船员或陆战队员 |

利润口径与本地参考版本一致，是已含税的贸易差价，未扣燃料/补给的消耗价值和后勤采购成本；后勤采购会实际扣减模拟资金。旅时包括星系内和超空间航行，不再额外增加每站 0.25 天；不模拟危险、风暴与未来行情。仅买卖新购货物，原有库存不自动出售。保留本项目已公开的参数语义：maxStops 为不同市场总数、闭环默认关闭、物资保留量默认 0，不引入参考 Mod 的阵营白名单或固定 100 天/100 光年默认储备。资源预算针对生成路线，后续回归玩家所需资源通过参数预留。

### 计划插入

成功的 `ExecutionResult` 可携带 `generatedPlan`；其他状态不得携带。Agent 检查新步骤契约、身份冲突并拒绝任何 RETURN 后，调用 `Plan.insertAfter(currentStep, generatedPlan)`，保留原目标和已有步骤身份，分配新的计划 ID，随后只推进一步。

例如 `计算 → 原后续步骤` 首先展开为 `计算 → 买入地 → 到站重算 A→B → 原后续步骤`；抵达 A 后再展开成 `到站重算 A→B → 后勤采购（如需）→ 买入 → 前往 B → 卖出 → 原后续步骤`。多段路线逐段处理，原有后续步骤不会被覆盖。两类决策成功都不代表交易完成，全部步骤结束后才验收业务目标并处理返航授权。展开计划、执行历史和进度一并存档，读档不会重复插入已完成决策的结果。

计算期间 Agent 暂缓普通模型重规划，保留定时触发；新后勤建议和持续短缺的周期复查均可在计算期间交轻量模型判断，不直接中断计算；轻量模型要求重规划并生成有效新计划后才切换。计算结束后按最新展开计划和执行历史重规划。展开会增加进度版本，之前的模型结果不能覆盖新计划。

## 监视器（Monitor）

`execution.Monitor` 是无状态的检查器，接收 `ExecutionResult` 和可选的 `FleetResources` 数值快照。执行状态与资源检查分别返回结论，不读取游戏对象或启动规划：

| 执行结果 | 检查结论 |
| --- | --- |
| `RUNNING / WAITING` | `CONTINUE`：当前步骤继续 |
| `SUCCEEDED` | `ADVANCE`：当前步骤完成，可以推进 |
| `FAILED` | `REPLAN`：需要重新规划 |

Monitor 不持有 Planner、Executor、计划进度或计时器，也不调用模型。Agent 根据检查结论执行推进、结束或规划操作。

建议触发线：燃料 `每光年油耗 × 15`、补给 `每日消耗 × 30`、船员 `getMinCrew()`；正好达到不触发，零消耗不产生对应建议。`ResourceCheck` 只含 READY/ADVISORY、实际快照、issues 和明确标注为建议的 reason，没有采购数量或目标持有量。油箱满油航程不足 15 光年同样只是 fuelCapacity 建议，不自动停机或要求玩家介入。

Agent 在每轮执行前、Monitor 检查实际结果时以及提交初始/周期重规划前读取资源。成功步骤先记入进度，再处理短缺，避免重做已完成交易；RETURN 合并成功后不再检查已移除分舰队的空货舱。暂停的 advance 不推进检查和执行；接收新任务时仍采集初始规划快照。

新建议只排队一次轻量检查，不暂停当前计划、不取消在途请求、不改变执行版本；同一建议按 15 秒周期复核，新问题出现则再次提交。轻量模型 KEEP 时继续原计划，REPLAN 时交主模型结合任务决定采购与数量，主模型收到轻量判断依据。请求过期后仍先轻量复核，不因过期直接强制补购。真正的步骤失败保留原失败处理。

后勤健康是持续任务的首要规划原则。缺员或燃料、补给短缺时，轻量模型通常选择 REPLAN；主规划器先安排抵达市场与补充，完成后再调用跑商计算器。已有有效补充前缀时保留计划；只有无可达库存、需先卖货筹钱或容量无法达到等明确例外才暂缓，并解释原因。采购量结合实际缺口、途中消耗和后续行程留出合理余量，无固定采购数或比例。玩家明确数量仍照办；执行器不增加资源门槛。

`worldState.resourceMarkets` 提供全星区可达渠道中最近 24 个的真实库存、到场容量、旅时、途中消耗和 `sampleQuantity/sampleTotalPrice` 整批价格样例（含黑市）。价格样例不是建议采购量，不能当单价使用；没有燃料加满、补给固定天数或船员比例要求。Agent 不审核补购数量或采购前缀，执行器按计划数量成交并检查实际库存、资金等交易条件。目标完成由原始任务验收，不将后勤建议追加为目标。

## 智能体（Agent）循环

`com.mozhi.fleet.Agent` 在游戏主线程协调 Planner、Executor 与 Monitor，持有任务和计划进度：

- `RUNNING / WAITING`：继续当前步骤；每轮最多执行一步。
- `SUCCEEDED`：先插入结果携带的 Plan，再推进下标，全部步骤成功后进入 `REVIEWING`，额外调用一次 LLM 验收原始目标。
- `FAILED`：暂停执行，取消已失效的在途周期检查，并携带失败历史直接交主模型重新规划；资产状态不确定时直接阻塞。
- 默认每 15 秒重新规划，可通过构造器调整。目标偏差由 Planner 根据最新世界状态和历史判断。
- 规划期间继续执行有效的旧计划；忙碌期间的触发合并为一次。步骤成功或失败后，旧版本规划结果会被丢弃并重新请求。
- `KEEP` 保留进度；替换计划时可续接相同的当前步骤；`GOAL_REACHED` 在常规规划中触发独立验收，在验收中确认成功，`BLOCKED` 停止任务。
- 周期规划失败时继续有效的旧计划，下一周期再请求；没有可执行计划时进入阻塞状态。

### 返航权限

Planner 的动作契约不含 `RETURN`，普通计划及计算器产生的子计划均不能携带返航。`order` 的 `returnAfterCompletion` 默认 false；聊天工具仅在玩家明确要求“达成目标后回来”时设 true。授权随任务保存，新任务重新授权；不会从规划器的输出获取授权。明确的 `recall` 命令由 `Agent.recall()` 直接执行。

验收成功时，没有授权就完成业务任务并待命，状态标记 `awaitingReturnConfirmation=true`，主对话智能体主动报告任务结束并询问是否返航。通知不调用行动工具，须等玩家答复；保持相同状态期间只发一次。有授权则由 Agent 新建返航步骤，实际合并后结束，不再对已移除的分舰队验收业务目标。普通周期规划不能提前宣告任务结束，会先触发独立验收。

### 验收结果

请求的 `completionReview=true` 表示验收阶段。模型结合原始目标、当前世界状态、执行历史和实际交易收据判断：确认达成返回 `GOAL_REACHED` 并结束；明确未达成返回 `REPLACE`，同次调用生成剩余计划继续执行；无法确定或无法继续返回 `BLOCKED`，通过现有对话通知请玩家检查。`KEEP`、无效响应或调用失败也进入人工检查，不能把调用失败当作目标达成。

验收等待期间不执行动作，也不按 15 秒重复提交验收。任务替换会取消旧验收；存档保留验收阶段，读档后重新请求验收，不重做已完成步骤。返航前先验收业务目标，不能把最终返航措辞当作业务目标未完成。比如“拥有 100 万再回来”检查分舰队实时余额，而非销售总额或预计利润。确认原始目标达成即可结束；仍需继续时按资源约束安排补购。

```java
Agent agent = new Agent(planner, executor, () -> collectWorldState());
agent.start(goal);
// 游戏主循环传入未加速的真实秒数增量；暂停期间不累计时间、不执行或接纳计划。
agent.advance(realElapsedSeconds, sector.isPaused());
Agent.View state = agent.view();
```

`collectWorldState()` 由接入层实现，在主线程采集文本快照。`view()` 提供任务、计划、步骤下标、最近结果、规划状态及原因；状态包括 `IDLE / PLANNING / EXECUTING / REVIEWING / COMPLETED / BLOCKED / CANCELLED`。外部事件可调用 `requestReplan(reason)`，下一轮更新时提交；`cancel()` 停止当前任务，`close()` 同时关闭 Planner。`start()` 替换旧任务并清空执行历史，迟到的旧任务响应不会被接纳。

## 游戏接入与测试

`FleetAgentHost` 加载 `game.FleetRuntime`，由主线程每帧调用 Agent。真实时间通过单调时钟计算，不受游戏加速倍率影响；暂停期间不累计规划时间。`GameWorld` 采集舰队资产、实际目的地 ID、市场和相关库存，供 Planner 规划。其他市场只提供目录信息，库存未知时不编造。

派遣后舰队原地待命。目前支持购买、出售、移动、持续跟随、回归，以及生成买卖计划的跑商计算器。明确地点的移动、跟随和召回可直接创建 Plan，自然语言复合任务由 Planner 生成。跟随不用旧版原生跟随任务；玩家可通过 stopMozhiFleet 取消，目标消失后失败并触发正常重规划。

派遣和买卖不以操作后资源储备、最低船员或超载作为拒绝条件，按明确授权的数量转移；预览建议没有最低划拨门槛。真实库存/资金不足则整笔报错且不部分成交；派遣失败按普通对话工具错误返回，子舰队动作失败由 Agent 请求重规划。资产恢复检查仍用于保证失败不会丢失或复制资产。

游戏存档只写 JSON 字符串（键 `mozhi_assistant_fleet_agent_v2`），不保存私有类加载器对象或 Future。读档后恢复执行下标，未结束的规划重新取快照提交。旧版存档只接管原舰队资产，需重新下达任务，旧计划不自动执行。

建议依次测试：指定非旗舰及资金物资派遣 → 前往市场入轨 → 少量购买/出售 → 保存读档确认进度 → 召回确认资产合并。解除暂停才会执行；状态面板可查看每步结果。复杂模组市场和真实模型响应仍以游戏内结果为准。

## 架构进度

- **Planner（已实现）**：根据原始目标、世界状态和最近 20 步执行结果，异步生成候选计划。
- **Executor（已实现）**：不调用 LLM，执行指定步骤；四种游戏动作和跑商决策动作放在 actions 目录中，结果写入历史窗口。
- **Monitor（已实现）**：检查执行结果及资源数值快照，返回步骤推进、资源重规划或容量不足的介入结论；不负责调度。
- **Agent 循环（已实现）**：管理任务与计划进度，按 Monitor 结论推进；按可配置间隔（默认 15 秒）触发规划、合并忙碌期间的触发、接纳有效候选计划。

- **游戏桥接（已实现）**：派遣、世界状态、主循环、聊天工具、状态面板、JSON 存档与类加载生命周期。
